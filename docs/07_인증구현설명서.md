# 인증 구현 설명서 — Plan Do See Diary (T07)

> ④는 실제 배포 주소(https://plandosee-noi8.vercel.app/)에서 브라우저 개발자 도구(Network 탭) 또는 `verify.sh`(프로젝트 루트)로 직접 만든 뒤, 아래 자리에 그대로 옮겨 적는다. 비밀번호·토큰·비밀키는 반드시 가려서(`eyJhb…생략`) 적는다.

## ① 무엇으로 붙였나

**Supabase Auth** (이메일 + 비밀번호 방식). Postgres(Supabase가 관리)에 `auth.users` 테이블로 계정을 저장하고, `supabase-js@2`(CDN, ESM) 클라이언트로 가입·로그인·로그아웃을 호출한다.

## ② 왜 그걸 골랐나

- **함께 검토했지만 고르지 않은 방법 1 — 직접 구현(Node/Express + bcrypt + 세션 테이블)**: 비밀번호 해싱·세션 무효화·토큰 재발급을 전부 손으로 관리해야 해서, 이번 과제 범위(6~8시간)에서 실수 없이 구현하기엔 위험이 컸다. 특히 "로그아웃 뒤 이전 토큰이 통하지 않아야 한다(T07-C114)"를 직접 구현하려면 서버 쪽 토큰 블랙리스트/세션 테이블을 따로 관리해야 하는데, 이번 프로젝트가 정적 사이트(Vercel, 서버 상시 구동 없음) 구조라 별도 백엔드 서버를 새로 두는 것이 부담이었다.
- **함께 검토했지만 고르지 않은 방법 2 — NextAuth.js**: Next.js 프레임워크 종속이 강해, 현재 순수 HTML/CSS/JS + Vercel 정적 배포 구조를 프레임워크 전체로 갈아엎어야 했다. T06에서 만든 UI를 그대로 재사용하기 어려워 제외했다.
- **선택 이유**: Supabase는 인증(비밀번호 해싱·JWT 세션·이메일 확인)과 데이터베이스(Postgres)를 함께 제공하고, **행 단위 보안(RLS)**으로 "서버가 소유자를 확인"하는 카드 4 요구사항을 애플리케이션 코드가 아니라 데이터베이스 레벨에서 강제할 수 있다. 정적 사이트에서 별도 백엔드 서버 없이도 `supabase-js` 클라이언트만으로 안전하게 붙일 수 있다는 점이 결정적이었다.
- **버전**: `@supabase/supabase-js@2` (CDN: `https://cdn.jsdelivr.net/npm/@supabase/supabase-js@2/+esm`)

## ③ 어디를 어떻게 고쳤나

| 흐름 | 지나는 파일/위치 |
|---|---|
| 가입 | `index.html`의 `#auth-form` → `script.js`의 `authForm submit` 핸들러 → `auth.js`의 `signUp()` → Supabase `auth.users` 테이블에 계정 생성 |
| 로그인 | 위와 동일 경로, `signIn()` → Supabase가 JWT 액세스 토큰 + 리프레시 토큰 발급 → `supabase-js`가 `localStorage`에 세션 저장 |
| 로그아웃 | `#logout-btn` → `script.js` → `auth.js`의 `signOut({scope:'global'})` → Supabase 서버 쪽 리프레시 토큰도 함께 무효화 |
| 자료 조회 | `script.js`의 `loadRecords()` → `supabase.from('records').select('*')` → Postgres RLS 정책(`supabase-schema.sql`)이 `auth.uid() = user_id`인 행만 반환 |
| 소유자 검증 | 애플리케이션 코드가 아니라 **DB 레벨**: `supabase-schema.sql`의 `select/insert/update/delete own records` 정책 4개 |
| 로그인 게이트 | `index.html`은 `#auth-screen`을 기본으로 보여주고 `#app-screen`은 `is-hidden`. `script.js`의 `onAuthChange()` 콜백이 세션 유무에 따라 두 화면을 토글 |

새로 만든 파일: `auth.js`(인증 래퍼), `config.js`(Supabase URL/anon key), `supabase-schema.sql`(테이블+RLS+계정삭제 RPC). 기존 T06의 `script.js`는 저장소를 `localStorage`에서 Supabase 호출로 전면 교체했다.

## ④ 안 열리는 것을 확인한 기록

> 아래 다섯 항목을 실제로 실행한 뒤 요청/응답을 그대로 옮겨 적는다. `verify.sh`의 안내 주석을 참고. 비밀값은 `eyJhb…생략` 형태로 가린다.

### (1) 로그인하지 않고 자료를 직접 요청 — 거절 확인 (T07-C97, C124)
```
요청:
GET {SUPABASE_URL}/rest/v1/records
Header: apikey: eyJhb…생략 (anon key)
(Authorization 헤더 없음 = 비로그인 상태)

응답:
(여기에 실제 상태 코드와 본문을 붙여넣기 — RLS 정책상 빈 배열([])이 예상됨)
```

### (2) 로그인 상태 성공 응답 vs 로그아웃 뒤 같은 값으로 재요청 — 거절 확인 (T07-C109, C110)
```
① 로그인 상태:
GET {SUPABASE_URL}/rest/v1/records
Header: apikey: eyJhb…생략
Header: Authorization: Bearer eyJhb…생략 (로그인 시 발급된 액세스 토큰)
응답: (붙여넣기 — 200 + 내 기록 목록)

② 로그아웃 후 같은 토큰으로 재요청:
GET {SUPABASE_URL}/rest/v1/records
Header: apikey: eyJhb…생략
Header: Authorization: Bearer eyJhb…생략 (①과 동일한, 이미 로그아웃된 토큰)
응답: (붙여넣기 — 401 예상, "JWT expired" 또는 "invalid token")
```

### (3) 다른 계정의 자료 읽기/수정/삭제 — 양방향 거절 확인 (T07-C117~120)
```
계정 A로 로그인해 계정 B의 기록 id(예: b_record_id)를 대상으로:

GET   {SUPABASE_URL}/rest/v1/records?id=eq.b_record_id
PATCH {SUPABASE_URL}/rest/v1/records?id=eq.b_record_id   body: {"value": 999}
DELETE {SUPABASE_URL}/rest/v1/records?id=eq.b_record_id
(모두 Authorization: Bearer <A의 토큰>)

응답: (세 요청 모두 붙여넣기 — 200 + 빈 배열([]) 예상. RLS는 "존재를 감추는" 방식이라
       404/403 대신 빈 결과로 응답하고, 실제로 아무 행도 바뀌지 않는다.)

반대 방향(B로 로그인해 A의 기록 대상)도 동일하게 반복해 붙여넣기.

거절 앞뒤로 상대 계정의 기록 건수 비교:
- 시도 전: B 계정 기록 (n)건
- 시도 후: B 계정 기록 (n)건 — 동일함을 확인
```

### (4) 주소·헤더·본문에 다른 계정 정보를 넣어 보내도 내 자료만 옴 (T07-C123)
```
GET {SUPABASE_URL}/rest/v1/records?user_id=eq.<다른 계정의 UUID>
Header: Authorization: Bearer <내 토큰>

응답: (붙여넣기 — 여전히 내 기록만 오거나 빈 배열. records.user_id 컬럼을
       내가 조작해서 조회 조건에 넣어도, RLS의 select 정책이 결과를 다시
       auth.uid()=user_id로 한 번 더 걸러내기 때문.)
```

### (5) 목록 응답에 남의 자료가 섞이지 않음 (T07-C125)
```
계정 A로 로그인한 상태에서:
GET {SUPABASE_URL}/rest/v1/records
응답 전체를 열어 모든 행의 user_id가 A 자신의 UUID와 같은지 확인.
(붙여넣기 — 응답 배열의 각 항목 user_id 나열)
```

## ⑥ 아직 못 막은 것

> 비워두지 않는다. "다 막았다"보다 정직하게 못 막은 것을 적는 쪽이 좋은 제출물이다. 아래는 이 구현이 실제로 다루지 않은 것들이다 — 검증 후 실제 상황에 맞게 다듬는다.

- **무차별 대입(brute-force) 로그인 시도 제한 없음**: Supabase 기본 설정은 특별한 rate limit을 프로젝트 코드 레벨에서 추가로 걸지 않는 한, 짧은 시간에 여러 번 틀린 비밀번호를 시도하는 것을 우리 쪽 코드가 막지 않는다. (Supabase 플랫폼 자체의 기본 rate limit에 의존 — 프로젝트별로 별도 확인 필요.) 왜 위험한가: 공격자가 자동화 도구로 비밀번호를 무작위 대입해 계정을 탈취할 수 있다.
- **비밀번호 재설정(이메일 인증 기반) 흐름 미구현**: 가입/로그인/로그아웃만 붙였고, "비밀번호를 잊었어요" 흐름은 만들지 않았다. 왜 위험한가: 실사용자가 비밀번호를 잊으면 복구 수단이 없어 계정이 사실상 잠긴다.
- **2단계 인증(2FA) 없음**: 이메일+비밀번호 단일 요인만 사용. 왜 위험한가: 비밀번호가 유출되면 그것만으로 계정이 뚫린다.
- **로그·감사 기록을 별도로 남기지 않음**: 로그인 실패/성공 이력을 애플리케이션 레벨에서 따로 기록하지 않는다(Supabase 대시보드의 기본 로그에만 의존). 왜 위험한가: 이상 로그인 시도를 우리 쪽에서 능동적으로 탐지하기 어렵다.
