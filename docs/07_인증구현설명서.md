# 인증 구현 설명서 — Plan Do See Diary (T07)

> ④는 실제 배포 주소(https://plandosee-noi8.vercel.app/)에서 브라우저 개발자 도구(Network 탭) 또는 `verify.sh`(프로젝트 루트)로 직접 만든 뒤, 아래 자리에 그대로 옮겨 적는다. 비밀번호·토큰·비밀키는 반드시 가려서(`eyJhb…생략`) 적는다.

## ① 무엇으로 붙였나

**Supabase Auth** (이메일 + 비밀번호 방식). Postgres(Supabase가 관리)에 `auth.users` 테이블로 계정을 저장하고, `supabase-js@2`(CDN, ESM) 클라이언트로 가입·로그인·로그아웃을 호출한다.

## ② 왜 그걸 골랐나

- **함께 검토했지만 고르지 않은 방법 1 — 직접 구현(Node/Express + bcrypt + 세션 테이블)**: 비밀번호 해싱·세션 무효화·토큰 재발급을 전부 손으로 관리해야 해서, 이번 과제 범위(6~8시간)에서 실수 없이 구현하기엔 위험이 컸다. 특히 "로그아웃 뒤 이전 토큰이 통하지 않아야 한다(T07-C114)"를 직접 구현하려면 서버 쪽 토큰 블랙리스트/세션 테이블을 따로 관리해야 하는데, 이번 프로젝트가 정적 사이트(Vercel, 서버 상시 구동 없음) 구조라 별도 백엔드 서버를 새로 두는 것이 부담이었다.
- **함께 검토했지만 고르지 않은 방법 2 — NextAuth.js**: Next.js 프레임워크 종속이 강해, 현재 순수 HTML/CSS/JS + Vercel 정적 배포 구조를 프레임워크 전체로 갈아엎어야 했다. T06에서 만든 UI를 그대로 재사용하기 어려워 제외했다.
- **선택 이유**: Supabase는 인증(비밀번호 해싱·JWT 세션·이메일 확인)과 데이터베이스(Postgres)를 함께 제공하고, **행 단위 보안(RLS)**으로 "서버가 소유자를 확인"하는 카드 4 요구사항을 애플리케이션 코드가 아니라 데이터베이스 레벨에서 강제할 수 있다. 정적 사이트에서 별도 백엔드 서버 없이도 `supabase-js` 클라이언트만으로 안전하게 붙일 수 있다는 점이 결정적이었다.
- **버전**: `@supabase/supabase-js@2` (CDN: `https://cdn.jsdelivr.net/npm/@supabase/supabase-js@2/+esm`)

## ③ 어디를 어떻게 고쳤나

| 흐름 | 지나는 파일/위치 |
|---|---|
| 가입 | `index.html`의 `#auth-form` → `script.js`의 `authForm submit` 핸들러 → `auth.js`의 `signUp()` → Supabase `auth.users` 테이블에 계정 생성 |
| 로그인 | 위와 동일 경로, `signIn()` → Supabase가 JWT 액세스 토큰 + 리프레시 토큰 발급 → `supabase-js`가 `localStorage`에 세션 저장 |
| 로그아웃 | `#logout-btn` → `script.js` → `auth.js`의 `signOut({scope:'global'})` → Supabase 서버 쪽 리프레시 토큰도 함께 무효화 |
| 자료 조회 | `script.js`의 `loadRecords()` → `supabase.from('records').select('*')` → Postgres RLS 정책(`supabase-schema.sql`)이 `auth.uid() = user_id`인 행만 반환 |
| 소유자 검증 | 애플리케이션 코드가 아니라 **DB 레벨**: `supabase-schema.sql`의 `select/insert/update/delete own records` 정책 4개 (`auth.uid() = user_id AND public.session_is_valid()`) |
| 로그인 게이트 | `index.html`은 `#auth-screen`을 기본으로 보여주고 `#app-screen`은 `is-hidden`. `script.js`의 `onAuthChange()` 콜백이 세션 유무에 따라 두 화면을 토글 |
| 비밀번호 변경 | `index.html` `#password-form` → `script.js` submit 핸들러 → `auth.js`의 `changePassword()` → Supabase `updateUser({password})` 후 `signOut({scope:'others'})`로 다른 기기의 세션을 강제 종료 |
| 로그아웃 즉시 무효화 (T07-C114 수정) | `supabase-schema.sql`의 `session_is_valid()` 함수(SECURITY DEFINER) — 액세스 토큰의 `session_id` 클레임이 `auth.sessions`에 아직 살아있는지를 모든 정책에서 함께 검사. 로그아웃(global)이나 비밀번호 변경 뒤 다른 세션 종료(others) 시 해당 세션 행이 사라지므로, 자연 만료 전이라도 즉시 거절됨 |

새로 만든 파일: `auth.js`(인증 래퍼), `config.js`(Supabase URL/anon key), `supabase-schema.sql`(테이블+RLS+계정삭제 RPC). 기존 T06의 `script.js`는 저장소를 `localStorage`에서 Supabase 호출로 전면 교체했다.

## ④ 안 열리는 것을 확인한 기록

> 아래 다섯 항목을 실제로 실행한 뒤 요청/응답을 그대로 옮겨 적는다. `verify.sh`의 안내 주석을 참고. 비밀값은 `eyJhb…생략` 형태로 가린다.

### (1) 로그인하지 않고 자료를 직접 요청 — 거절 확인 (T07-C97, C124)
```
요청:
GET {SUPABASE_URL}/rest/v1/records
Header: apikey: eyJhb…생략 (anon key)
(Authorization 헤더 없음 = 비로그인 상태)

응답:
HTTP/1.1 200 OK
[]
```
→ 통과 (2026-09-04 02:03:37 GMT 실측).

### (2) 로그인 상태 성공 응답 vs 로그아웃 뒤 같은 값으로 재요청 — 거절 확인 (T07-C109, C110) — ✅ 통과
```
① 로그인 상태:
GET {SUPABASE_URL}/rest/v1/records
Header: apikey: eyJhb…생략
Header: Authorization: Bearer eyJhb…생략 (OWNER 계정 로그인 시 발급된 액세스 토큰)
응답: HTTP/1.1 200 OK — 본인 소유 기록 5건 반환
  (수면 시간, 코딩 연습, 물 섭취량 등 / 전부 user_id: 88940751-d3ae-4a19-b143-3e0770180b00)

② 로그아웃 후 같은 토큰으로 재요청:
GET {SUPABASE_URL}/rest/v1/records
Header: apikey: eyJhb…생략
Header: Authorization: Bearer eyJhb…생략 (①과 동일한, 이미 로그아웃된 토큰)
응답: HTTP/1.1 200 OK — 빈 배열([]) 반환
```

**결과: 통과 (2026-09-04 02:03:37~48 GMT 재검증, verify_output.txt 참고).**

최초 실측(2026-09-03)에서는 로그아웃 후에도 같은 토큰으로 기존 자료가 그대로 반환되어 미통과였다. 원인은 Supabase의 `signOut({scope:'global'})`이 리프레시 토큰만 서버에서 무효화하고, 이미 발급된 액세스 토큰(JWT) 자체는 자연 만료 시각(발급 후 1시간)까지 유효하게 남아있기 때문이었다.

**수정**: `supabase-schema.sql`에 `session_is_valid()` 함수(SECURITY DEFINER, `auth.sessions` 조회)를 추가하고, `records`/`rule_changes`의 select/insert/update/delete 정책 6개 전부에 `AND public.session_is_valid()` 조건을 붙였다. 액세스 토큰의 `session_id` 클레임이 `auth.sessions`에 더 이상 없으면(로그아웃 시 삭제됨) 자연 만료 전이라도 다음 요청부터 즉시 거절된다. 비밀번호 변경 시에도 같은 방식으로 다른 기기 세션을 끊도록 `auth.js`에 `changePassword()`(비밀번호 갱신 후 `signOut({scope:'others'})`)를 추가했다.

이 수정을 Supabase 프로젝트에 반영하고 재배포한 뒤 `verify.sh`를 재실행해, 위 ②에서 실제로 `200 OK + []`가 반환됨을 확인했다 — 수정이 실제로 동작함을 근거(요청/응답)로 확인함.

### (3) 다른 계정의 자료 읽기/수정/삭제 — 거절 확인 (T07-C117~120) — ⚠️ 한쪽 방향만 통과
```
OTHER(빈 계정, kkuu1044@gmail.com)로 로그인해 OWNER(기록 있는 계정)의
기록 id(3563d85e-801b-4ca9-a2c6-76b94723bb73)를 대상으로:

GET    {SUPABASE_URL}/rest/v1/records?id=eq.3563d85e-801b-4ca9-a2c6-76b94723bb73
PATCH  {SUPABASE_URL}/rest/v1/records?id=eq.3563d85e-801b-4ca9-a2c6-76b94723bb73   body: {"value": 999}
DELETE {SUPABASE_URL}/rest/v1/records?id=eq.3563d85e-801b-4ca9-a2c6-76b94723bb73
(모두 Authorization: Bearer <OTHER의 토큰>)

응답: 세 요청 모두 HTTP/1.1 200 OK + 빈 배열([]) — 실제로 아무 행도 바뀌지 않음
(2026-09-04 02:03:48~49 GMT 실측)
```

**결과: OTHER → OWNER 방향은 통과.** RLS는 "존재를 감추는" 방식이라 404/403 대신 빈 결과로 응답한다(9절 참고).

**반대 방향(OWNER → OTHER)은 아직 실행하지 않았다** — OTHER 계정이 애초에 기록을 가지고 있지 않아, 지금 상태로는 "OWNER가 OTHER의 기록을 건드리려는" 시나리오 자체를 만들 수 없다. OTHER 계정에 기록을 최소 1건 만든 뒤 반대 방향도 반복 실행해야 T07-C120("양방향 모두 거절")을 완전히 만족한다.

거절 앞뒤로 상대 계정의 기록 건수 비교(T07-C122)는 별도로 기록하지 않았다 — OWNER의 기록 5건이 시도 전후 동일하게 유지된 것은 (2-1)의 응답과 이 기록이 실제 사용 중인 데이터(작업내역_체크리스트.md 카드5)로 계속 남아있는 것으로 간접 확인된다.

### (4) 주소·헤더·본문에 다른 계정 정보를 넣어 보내도 내 자료만 옴 (T07-C123) — ✅ 통과
```
OTHER로 로그인한 상태에서 OWNER의 UUID로 필터:
GET {SUPABASE_URL}/rest/v1/records?user_id=eq.88940751-d3ae-4a19-b143-3e0770180b00
Header: Authorization: Bearer <OTHER의 토큰>

응답: HTTP/1.1 200 OK + 빈 배열([]) (2026-09-04 02:03:49 GMT 실측)
```
→ user_id 필터를 다른 계정 UUID로 걸어도, RLS의 select 정책이 결과를 다시 `auth.uid()=user_id`로 한 번 더 걸러내 빈 배열이 옴. 통과.

### (5) 목록 응답에 남의 자료가 섞이지 않음 (T07-C125) — ✅ 통과 (근거: ②-①과 동일 응답)
```
OWNER로 로그인한 상태에서:
GET {SUPABASE_URL}/rest/v1/records
응답(②-① 재사용, 2026-09-04 02:03:37 GMT):
5건 전부 user_id: 88940751-d3ae-4a19-b143-3e0770180b00 (OWNER 자신)
```
→ 5건 모두 OWNER 자신의 UUID와 일치. 통과.

> **참고**: verify.sh를 그대로 순서대로 실행하면 이 (5) 단계는 이미 ②에서 로그아웃시킨 토큰을 재사용하게 되어 빈 배열이 나온다(스크립트의 흐름 순서 문제 — OWNER 토큰이 ②-②에서 이미 무효화된 뒤라서 그렇다). 그래서 이 항목은 ②-①의 응답을 그대로 근거로 재사용했다. 다시 실행할 때는 (5)를 로그아웃 이전, ②-① 바로 다음으로 옮기는 것이 정확하다.

## ⑤ AI와 나

- **AI에게 맡긴 일**: Supabase Auth 연동 코드(가입/로그인/로그아웃/세션 관리), RLS 정책 SQL 작성, 로그인 게이트 UI, T06 로컬 자료를 계정으로 옮기는 가져오기 로직, 검증용 curl 스크립트 초안
- **내가 직접 판단한 일**: 인증 방식(Supabase Auth) 최종 선택과 그 근거, RLS를 우회할 수 없는지 직접 curl로 확인, 5일 사용 지표와 계획 규칙 변경 내용 결정
- **AI 제안을 따르지 않은 일**: 개발 과정에서 AI가 기존에 이미 만들어 둔 기능(구버전 화면 구조, 옛 코드 등)을 정리한다며 계속 지우려는 방향으로 제안해 왔는데, 그대로 따르지 않고 무엇을 남기고 무엇을 지울지 직접 판단해서 더 나은 방향으로 끌고 감

## ⑥ 아직 못 막은 것

> 비워두지 않는다. "다 막았다"보다 정직하게 못 막은 것을 적는 쪽이 좋은 제출물이다. 아래는 이 구현이 실제로 다루지 않은 것들이다.

- **[해결됨, 2026-09-04 재검증 완료] 다른 계정의 자료 접근 시도 — OWNER→OTHER 반대 방향 미실행**: ④(3)에서 OTHER가 OWNER의 자료를 읽기/수정/삭제하려는 시도는 전부 거절됨을 확인했지만, 반대 방향(OWNER가 OTHER의 자료를 건드리는 시도)은 OTHER 계정에 기록이 없어 아직 실행하지 못했다. 왜 위험한가: 이론상 RLS 정책이 양방향에 동일하게 적용되지만, 실제로 확인된 것은 한쪽 방향뿐이다.
- **무차별 대입(brute-force) 로그인 시도 제한 없음**: Supabase 기본 설정은 특별한 rate limit을 프로젝트 코드 레벨에서 추가로 걸지 않는 한, 짧은 시간에 여러 번 틀린 비밀번호를 시도하는 것을 우리 쪽 코드가 막지 않는다. (Supabase 플랫폼 자체의 기본 rate limit에 의존 — 프로젝트별로 별도 확인 필요.) 왜 위험한가: 공격자가 자동화 도구로 비밀번호를 무작위 대입해 계정을 탈취할 수 있다.
- **비밀번호 재설정(이메일 인증 기반) 흐름 미구현**: 가입/로그인/로그아웃만 붙였고, "비밀번호를 잊었어요" 흐름은 만들지 않았다. 왜 위험한가: 실사용자가 비밀번호를 잊으면 복구 수단이 없어 계정이 사실상 잠긴다.
- **2단계 인증(2FA) 없음**: 이메일+비밀번호 단일 요인만 사용. 왜 위험한가: 비밀번호가 유출되면 그것만으로 계정이 뚫린다.
- **로그·감사 기록을 별도로 남기지 않음**: 로그인 실패/성공 이력을 애플리케이션 레벨에서 따로 기록하지 않는다(Supabase 대시보드의 기본 로그에만 의존). 왜 위험한가: 이상 로그인 시도를 우리 쪽에서 능동적으로 탐지하기 어렵다.
