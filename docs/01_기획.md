# 기획 — 플랜두씨 다이어리

## 기술 스택

- 순수 HTML/CSS/JS, 빌드 도구·프레임워크 없음
- 폰트: Noto Serif KR(제목), Pretendard(본문) — Google Fonts / jsDelivr CDN
- 저장소: 브라우저 `localStorage`만 사용, 서버·백엔드 없음

## 디자인 콘셉트

"계획한 나"(파랑 잉크, `--plan`)와 "실제의 나"(호박색 잉크, `--actual`)가 한 장부 위에 나란히 기록되는 저널 콘셉트. 배경은 괘선이 은은하게 들어간 종이 톤(`--paper`), 표는 장부 스타일 괘선으로 구성.

## 데이터 구조

`localStorage` 키: `plandusy_diary_data`

```json
{
  "schemaVersion": 2,
  "lastMigration": "ISO 8601 문자열 또는 null",
  "records": [
    {
      "id": "고유 ID (crypto.randomUUID)",
      "date": "YYYY-MM-DD",
      "tz": "Asia/Seoul",
      "item": "항목 (예: 수면 시간)",
      "value": 6.5,
      "unit": "단위 (예: 시간)",
      "tag": "선택 태그 (예: 계획 / 실제)",
      "memo": "선택 메모"
    }
  ]
}
```

**v1(과거 형식)**: 최상위가 래퍼 없이 레코드 배열이며, 각 레코드에 `tag` 필드가 없음.

## 핵심 알고리즘

### 1) 날짜 검증 (`isValidDateStr`)
`YYYY-MM-DD` 정규식 통과 후, `Date` 객체로 재구성한 연/월/일이 입력값과 정확히 일치하는지 재확인한다. 이렇게 하면 `2024-02-30`처럼 JS `Date`가 자동으로 다음 달로 보정해버리는 값을 "잘못된 날짜"로 정확히 걸러낼 수 있다.

### 2) 주 경계 계산 (`startOfWeek`)
`Date.getDay()`(0=일요일~6=토요일) 기준으로 해당 날짜가 속한 주의 월요일 00:00을 계산한다. 일요일(`day===0`)은 -6일 이동, 그 외 요일은 `1-day`일 이동.

### 3) v1 → v2 마이그레이션 (`migrateToV2`)
1. 최상위가 배열이면 v1로 판단하고 레코드 목록으로 취급.
2. 객체이고 `schemaVersion===2 && records 배열`이면 이미 v2.
3. 그 외(래퍼는 있으나 버전 표기가 없는 경우 등)는 레거시로 취급.
4. 각 레코드에 `tag` 필드가 없으면 추가(`''` 기본값), 있으면 그대로 둔다.
5. 결과가 이미 v2이고 모든 레코드에 `tag`가 있으면 `wasLegacy=false`를 반환 — 이 값으로 재실행 시 아무 것도 바뀌지 않았음을 화면에 표시한다.

### 4) 주간 집계 (`renderSummary`)
1. 현재 선택된 주의 월~일 범위를 계산.
2. 각 레코드에 대해: 날짜가 유효하지 않으면 → 항상 "제외된 기록"에 사유와 함께 표시(어느 주에도 속하지 않으므로 주 필터와 무관하게 항상 노출).
3. 날짜는 유효하지만 선택된 주 범위 밖이면 → 조용히 건너뜀(다른 주의 기록이므로 이번 집계와 무관).
4. 선택된 주 범위 안이고 값이 숫자가 아니면 → "제외된 기록"에 사유와 함께 표시.
5. 나머지 유효한 레코드만 `항목|단위` 키로 그룹핑해 합계·건수 계산.

## 아직 다루지 않은 것 / 알려진 한계

- 시간대는 `Asia/Seoul` 고정이며 실제 타임존 변환 로직은 없다(로컬 브라우저 시각 기준 계산). 여러 시간대 사용자를 지원해야 하면 `date-fns-tz` 등의 도입이 필요.
- 대량 기록(수천 건 이상)에서의 렌더링 성능은 검증하지 않음 — 개인 다이어리 용도로 설계.

# T07 갱신 — 인증 붙이기

## 아키텍처 변화

| | T06 | T07 |
|---|---|---|
| 저장소 | 브라우저 `localStorage` | Supabase Postgres (계정별로 분리) |
| 접근 제어 | 없음(누구나 같은 브라우저에서 다 봄) | Supabase Auth 로그인 + RLS로 서버 단에서 소유자 검증 |
| 배포 | GitHub Pages | Vercel |
| 신규 파일 | — | `auth.js`, `config.js`, `supabase-schema.sql`, `verify.sh` |

## 데이터 구조 (Postgres, `supabase-schema.sql` 참고)

```
public.records
  id uuid, user_id uuid(FK auth.users), date, tz, item, value, unit, tag, memo, created_at

public.rule_changes
  id uuid, user_id uuid(FK auth.users), changed_at, content, reason
```

T06의 `localStorage` 스키마 버전 관리(`schemaVersion`, v1→v2 마이그레이션)는 이제 Postgres 테이블 자체의 컬럼으로 대체되어 별도 마이그레이션 로직이 필요 없다. 대신 T06 로컬 자료를 계정으로 옮기는 1회성 가져오기 로직(`script.js`의 `import-file` 핸들러)이 그 역할을 한다.

## 인증 흐름

가입/로그인은 `auth.js`의 `signUp`/`signIn`이 Supabase Auth REST API를 호출한다. 세션(JWT 액세스 토큰 + 리프레시 토큰)은 `supabase-js`가 자동으로 `localStorage`에 저장·갱신한다. 자료 조회/수정/삭제는 매 요청에 세션의 액세스 토큰이 `Authorization: Bearer` 헤더로 실려 가고, Postgres RLS 정책이 `auth.uid()`(토큰에서 추출한 사용자 ID)와 `records.user_id`를 비교해 행 단위로 허용 여부를 결정한다 — 즉 "서버가 주인을 확인"하는 부분은 애플리케이션 코드가 아니라 데이터베이스가 담당한다.

자세한 근거와 실제 확인 기록은 `docs/07_인증구현설명서.md` 참고.
